## Decisions

- **2026-10-28: Web app.** Anyone can open it from a link on their phone without installing anything; iOS was not an option on Windows anyway. Alternatives: Android, iOS, desktop.
- **2026-10-28: Scheduled fetch, not live scraping.** A scheduled job saves today's events and the site reads the saved copy, so there is no server to run or pay for and sources are not hit on every page load. Alternatives: fetch on each visit, or run locally.
- **2026-10-28: OneIllinois first, Instagram later.** OneIllinois (UIUC's club platform, run on CampusGroups) publishes a public event feed at `https://one.illinois.edu/rss_events` that its robots.txt does not block. Instagram restricts automated access, so it needs its own decision. Alternative considered: Campus Labs Engage, which UIUC turned out not to use.
- **2026-10-28: Free food = `foodProvided` flag or food words in the description.** The feed has a `foodProvided` field, but on this date only 24 of 3,174 upcoming events set it, and food words appear only about 40 times in the whole feed. Using both catches more; a second source will still be needed for the app to be useful most days.
- **2026-10-28: Vite + TypeScript, with the fetch script in TypeScript run by Node.** One language for the page and the scraper, no server. Each source is its own module that returns the shared `FoodEvent` shape (`src/events.ts`), so Instagram or student submissions can be added later without changing the page. Submissions would need somewhere to store them (a Google Form or small free database) as an add-on.
- **2026-10-28: Private GitHub repository** (`free-food-uiuc`), can be made public later. On 2026-10-29 Kabir renamed it to `free-food-at-uiuc` and made it public.
- **2026-10-29: Host on GitHub Pages, making the repo public.** GitHub Pages needs a public repo on the free plan, and Kabir was fine making it public; there are no secrets in it. A GitHub Actions job (`.github/workflows/deploy.yml`) fetches and redeploys four times a day and on every push. Alternative: keep it private and host on Cloudflare Pages or Netlify, which needs a second account and a deploy key.
- **2026-10-29: Design system in Tailwind CSS, with its defaults removed.** Kabir wanted the site to stop looking "vibe coded" and asked for research first (sources included zoer.ai's guide, the Fountain Institute, and impeccable.style), plus reference sites Kabir likes (Think Company, Lounge Lizard, Webflow, Eladio Dieste, Huddle). The common tells are default fonts and palettes, emoji as icons, colored side stripes, cards and shadows on everything, and generic copy. The reference sites share mostly neutral colors with one accent, few shadows, and small corners. Kabir suggested Tailwind instead of a separate DESIGN.md; its built-in theme is wiped (`--*: initial`) so only our values exist and off-system classes don't work. Colors and fonts follow the Illinois brand guide (Illini Blue #13294B, Illini Orange #FF5F05 only on the blue header since it fails contrast on white, darker #C2410C for small orange text; Montserrat headings, Source Sans body). Fonts are self-hosted rather than loaded from Google. Kabir chose no emoji at all and a neutral tone. Alternatives: plain CSS variables with a DESIGN.md, or Tailwind with its defaults (rejected, since its default theme is the generic look).
- **2026-10-29: Commits use GitHub's private noreply email** for this repo, since the repo is public. Earlier commits still show Kabir's Gmail; removing it would mean rewriting history.

- **2026-10-29: Contact us is an email link to kabirgan19@gmail.com.** Kabir chose a plain email link. The address is public on the site, so the page builds it in JavaScript rather than writing it into the HTML, which keeps most spam bots that scan pages from collecting it. Alternatives: a Google Form (keeps the email private) or GitHub issues (needs a GitHub account).
- **2026-10-29: Accounts with Supabase, Illinois emails only, sign-in optional.** Kabir wants signed-in students to save events, submit events, get notifications, and follow clubs or save preferences. The site has no server, so a hosted service holds accounts and data. Supabase was chosen: its free tier covers sign-in, a database, file storage (flyers), and server functions (flyer scanning, notifications) with no credit card. Its free projects pause after a week idle, so the scheduled fetch will touch the database each run. Firebase was the alternative, but it now needs a billing account for server functions and file storage. Sign-in is "Sign in with Google" limited to @illinois.edu (real NetID login isn't available to unofficial projects); the limit is enforced in the database, since a check only in the page could be bypassed. Browsing stays open to everyone. Only email and name are stored, with a privacy page and account deletion. Submitted events wait for Kabir's approval before appearing, so fake "free food" posts can't go up. Order: filters first (everyone benefits, no account needed), then accounts phases A to E.

- **2026-10-30: Google's own sign-in button instead of a redirect through Supabase.** With the redirect, Google's screen names the Supabase address, which Kabir said doesn't look trustworthy. Google's sign-in script signs the student in on our page and hands back a signed token that Supabase verifies, so Google names our site. The button is Google's standard white one rather than our blue style, because Google's script draws its own button (and it's familiar to people). The script loads only on the Account page. Alternatives: Supabase's custom domain add-on (paid), or a custom domain later.

- **2026-10-30: A "Menu" button on phones and an account menu, replacing the row of header links.** Kabir wanted a three-line menu "like most websites" so the header doesn't wrap on phones once more items are added, with saved events and other options under the profile after signing in. Research (Nielsen Norman Group's hamburger-menu study, accessibility guides) found hidden menus are slower to use, much more on desktop (about 39%) than on phones (about 15%), and that the icon works better with the word "Menu" beside it. So phones get a "Menu" button with three lines, while screens 640px and wider keep the links in a row (Claude's choice, open to Kabir overruling). Signed in, a round button with the student's initial opens Saved events, Account settings, and Sign out. Alternative: three lines on every screen size.
- **2026-10-30: Saved events keep a copy of the listing.** OneIllinois drops events once they end and the site's list only covers two weeks, so each saved row stores the event itself. The Saved page shows the latest listing when the event is still in it, and warns "may be cancelled" if it vanished before ending. Ended events are hidden; a daily job inside Supabase (`pg_cron`) deletes them a week after they end (Kabir's choice), so no extra server is needed.
- **2026-10-30: Wider layout, with text kept at reading width.** Kabir's laptop screenshot showed the content in a narrow column with wide empty margins. The page frame grows to 72rem, and Today and Calendar split into two columns on laptops, since one event row stretched across the screen would be hard to scan (Claude's choice, Kabir approved). Text-heavy pages keep 640px lines because long lines are tiring to read.
- **2026-10-30: Calendar as a month view with arrows.** Kabir found the two-week day picker cramped and asked for "a full month's worth like how a normal calendar would work". Calendar design guides (UX Planet, Cieden, Nielsen Norman Group) point to the paper-calendar layout: weekday names once across the top, fixed weekday columns, and today distinct from the chosen day. Kabir chose a month with arrows (this month and next) over a rolling five-week grid. OneIllinois lists events months ahead, so saving through the end of next month needs no new source.
- **2026-11-06: Read flyers with Gemini's free tier.** Kabir asked for a way to do this without paying and had a free Google key. Claude Haiku 5.5 (roughly 10 cents per 100 flyers, needs a prepaid account) and free text recognition in the browser (Tesseract.js, likely poor on stylized flyers) were the alternatives. Free-tier conditions Kabir accepted for now: Google may use uploads to improve its products and its reviewers may read them, so the upload warns against personal information and the privacy page explains this; users must be 18 or older and apps likely used by under-18s aren't allowed, though some freshmen may be 17; EU, UK, and Swiss users require the paid tier. The free limits appear only in AI Studio, so running out shows a message and the form still works by typing.
- **2026-11-06: How flyers are handled (Claude's choices).** A Supabase Edge Function holds the key, so it never reaches the browser. Flyers are shrunk in the browser and never stored, so admins don't see them on the review page. Each student gets 10 reads a day, and failed attempts count. The Gemini SDK is pinned to 2.31.0 because 3.0.0 came out the same day and Deno's safety rule blocks packages under a day old.
- **2026-11-06: Submit events before following clubs.** Claude suggested it because few OneIllinois events mention food, so following clubs would add little until there are more events; Kabir chose D. The form comes first, with flyer upload after it.
- **2026-11-06: Approved events appear at the next scheduled fetch.** Kabir chose this over having each visitor's page read Supabase, which would have shown them right away. Visitors still contact only the saved list, and an approved event waits for the next run unless someone starts the job by hand.
- **2026-11-06: Admins use the normal sign-in, plus a list in the database.** Kabir wants only Kabir and friends to be able to approve requests. Everyone signs in with the same Google button (Claude's choice over a separate admin login, so there's no extra password). Admin emails are stored only in the database's `admins` table because the repo is public. They're added with one line of SQL, and the database refuses decisions from anyone else. Review happens on a page on the site (Kabir's choice over editing rows in the Supabase dashboard).
- **2026-11-06: Ended submissions disappear on their own.** Kabir didn't want a bulk of old approved submissions building up. They leave the review page when the event ends and are deleted a week later by a daily job, matching saved events.
- **2026-11-06: An OneIllinois outage keeps the last published list; a Supabase outage doesn't.** With two sources, the old rule (fail only if every source is down) would have published a nearly empty list if only OneIllinois failed (Claude's choice).
- **2026-11-09: Following clubs, and filters still reset each visit.** Kabir chose following clubs over remembering filter choices, and dropped the latter, keeping the October choice that filters reset each visit. Before notifications exist, following marks the club's events, adds a "Clubs I follow" filter, and lists clubs on a Following page in the profile menu (Kabir moved the list there from Account settings). Clubs are stored by name, because OneIllinois and submissions share no club ID, and names that differ only in capitals or spacing count as one club (Claude's choice). Unfollowing needs no confirmation, since following again is one tap.
- **2026-11-09: A Club search box with the site's own suggestion list.** Kabir wanted to filter by club without a long list of clubs on screen. Claude suggested typing part of a name with suggestions, over a long checklist or a scrolling menu. The browser's built-in suggestions (`datalist`) were tried first, but Kabir said they didn't fit the site's look and browsers don't let sites style them, so the site draws its own list (ARIA combobox pattern, keyboard and screen reader support). Matching is "name contains what was typed" (Claude's choice), so a link to one club can also show a longer name containing it. The club from a Following link is removed from the address once read, so clearing the filter and refreshing doesn't bring it back.
- **2026-11-10: Search in the header of every page, with its own results page.** Kabir chose this over a box only on Today, which would mostly repeat the Filters panel's Club box. Results cover every upcoming event (today through the end of next month), so a search from any page can answer "when is the next pizza?". It searches name, club, location, event type, and food words, not descriptions, which aren't saved and would bring loose matches (Kabir agreed). Every word must match, so more words narrow the results (Claude's choice). To fit the box in the row, the first name beside the account button now shows from 1024px wide instead of 640px (Claude's choice).
- **2026-11-10: Google Calendar with the narrowest permission, in its own calendar.** The site asks only for `calendar.app.created`, which reaches only calendars the site creates, so it can never see or change a student's other events. Kabir checked in Google Cloud Console that it's non-sensitive, so no verification review is needed (`calendar.events` was the alternative, with reports of reviews taking weeks). A calendar subscription link was the fallback if a review had been needed. Kabir asked for an on/off switch, off by default, and chose that turning it off deletes the calendar rather than leaving it.
- **2026-11-10: How calendar sync works (Claude's choices).** No Google tokens are stored: the browser gets about an hour of access from Google, kept only in that tab, so a Google window may briefly open on the first star after that (the alternative, storing long-lived tokens in Supabase, would mean holding keys to students' calendars). Each Google event's ID is worked out from our event's ID, so unstarring deletes the right one without storing anything per event. The star asks Google before anything else, since browsers only let popups open during a tap. Turning the switch off asks on the page rather than in a browser popup for the same reason. Deleting an account can't reach Google, so the confirmation says to turn off Google Calendar first.
- **2026-11-10: Calendar updates happen in the browser, when the student is on the site.** Kabir chose this (option 1) over having the scheduled job update every connected calendar (option 2), which would mean storing long-lived Google keys. A student who never comes back doesn't get updates; option 2 can build on the same comparison if that turns out to matter. Changes are found by comparing exactly what would be sent to Google, so any visible difference counts. Possibly cancelled events are marked rather than deleted, since OneIllinois sometimes drops events by mistake (Claude's choice). The Account page's turn-off confirmation lost its colored side stripe, a "vibe coded" tell (Claude's choice).
- **2026-11-10: Followed clubs in the calendar (Kabir's choices).** A separate switch rather than always on, the same calendar rather than a second one, and an event leaves the calendar only when there's no reason left (not saved, and its club not followed with the switch on). A club's newly listed events are added when the student next taps something on the site, since there are no stored Google keys. Claude replaced the saved-events flag from 007 with a `calendar_events` record of what's in each calendar, so one comparison handles adding, updating, and removing for both reasons (008 drops the old column). The second switch turns back off if Google can't be updated, so it matches the calendar (Claude's choice).

## Problems

- **2026-11-10: Google Calendar seemed slow to show changes (about a minute).** The site's messages appeared right away, so the delay was Google Calendar's open tab only refreshing every so often. Reloading the Google Calendar tab (or pulling down in the phone app) shows changes at once. No code change.

- **2026-11-10: Connecting Google Calendar failed twice during setup.** First "Couldn't check whether Google Calendar is connected": the new table didn't exist yet because the SQL hadn't been run. Then "Google didn't accept the site's access": the Calendar API was off in the project holding the sign-in client. The error message now includes Google's own reason, which named the project and the fix.

- **2026-11-06: The first version of the submissions script would have refused every submission.** The "at most 10 waiting" rule queried the table it protects, which Postgres rejects as infinite recursion. Testing the script in a throwaway Postgres database (PGlite) caught it before it reached Supabase. Fix: the count runs in its own `security definer` function.
- **2026-10-30: Google sign-in failed with "Unable to exchange external code".** The Client secret in Supabase didn't match the Google client (Google only shows a secret once, so it's easy to paste the wrong one). Fix: add a new secret on the Google client and paste it into Supabase's Google provider. The Account page first showed only "Sign-in didn't work"; it now includes Supabase's error text so problems like this can be diagnosed.
- **2026-10-29: Today's events vanished once they ended.** OneIllinois removes events from its feed as soon as they end, so after the evening fetch the site had no record of today's earlier events. Fix: each fetch carries over today's ended events from the previous copy (the live site's `events.json` in GitHub Actions). Events that vanish before their end time are treated as cancelled and dropped.
- **2026-10-29: A food drive showed up as free food.** "Pious Projects Feed the Hungry Food Drive" got through because its listing also mentioned lunch for volunteers. Fix: events whose title says food drive, food pantry, canned food, or donate food are skipped, with a test for this case.
